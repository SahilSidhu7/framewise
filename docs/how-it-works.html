How Framewise works

A plain-language guide to the whole project: what runs where, what happens when you ask for an edit, how the automatic editing makes its decisions, and how it was built. Each part says whether it exists today or is still planned.

01

In one minute

Framewise is a desktop photo and video editor for Windows. You describe the result you want ("cinematic travel video, 60 seconds, with music"), and it produces three finished versions you can preview, pick from and then change by hand. It can also turn one long video into several short, captioned vertical reels.

Everything runs on your own computer. There is no server of ours involved in editing: the speech recognition and the language model run locally, and your files are never uploaded.

The one idea to remember. The model never touches pixels and never edits your project directly. It writes a short edit program (a few lines of text in our own Edit DSL). The engine checks that program, turns it into normal timeline changes, and renders it. That is why every automatic edit is previewable, editable, and one Undo away.

02

The pieces

There are two programs and a few local helpers. The app is the window you see (React interface inside a small Rust shell, built with Tauri). The engine is a Python program that does all the real work. The app starts the engine in the background and talks to it over a private connection on your own machine.

03

A photo edit, step by step

  1. Measure the photo. On import the engine computes exposure, highlight and shadow clipping, white balance and colour cast, contrast, saturation, noise and sharpness. These numbers are cached.
  2. Write a brief. The measurements become a few lines of plain text, for example "slightly underexposed, warm cast, low contrast". Text is cheaper and more precise for a small model than raw pixels.
  3. Read the request. Your words and the style/output options become hints: which looks fit "vintage", whether cropping was asked for, whether you only want fixes.
  4. Ask the model, with a fence around it. The model is given the brief, the hints, the list of tools and their ranges, and a grammar that only allows valid edit programs (at most one look, a few corrections, a few finishing touches).
  5. Check the answer. A sanitiser re-checks the program: only one look, and only an allowed one; adjustment sizes capped to safe limits; exposure may only move the way you asked or the measurements call for; a white product background is never darkened; colour temperature may not fight a "warm" or "cool" request.
  6. Show three versions. The program runs three times with different creativity, each rendered as a preview; the first is applied as one Undo step.
# warm up the food and lift the shadows; keep it natural
white_balance temp=+8
adjust exposure=+0.25 shadows=+20 contrast=+8
look film_portra s=0.6
vignette 0.15

If the local model is not installed, a rule-based planner produces the same kind of program from keywords, so the feature still works, just less flexibly.

04

A video edit, step by step

Video is split into two jobs. The model chooses the intent (shape, pace, transitions, look, captions, music). Ordinary code, called the director, turns that intent into an exact cut list. A small model is good at the first job and bad at the second, so it only does the first.

  D --> E["Guard rules

  E --> F["Director (plain code)

  F --> G["Edit program (Video DSL)"]
  G --> H["Timeline commands
one Undo step"]
  H --> I["Preview and export"]

An intent is tiny. This is all the model writes for one version:

# calm travel film: slow cuts, warm cinematic grade, music under
aspect 16:9
pace slow
transition crossfade
look teal_orange_cinematic s=0.7
grain 0.12
letterbox 2.39
music 3

The director then expands it into the full program: which clip, which seconds, in what order, with which transitions, aligned to the music. That expanded program is what you see in the timeline.

05

How auto edit decides

TODAYNo custom model has been trained yet. The "brain" is Qwen3-1.7B (Apache 2.0 licence), an off-the-shelf small language model, quantised to 8-bit (about 1.8 GB) and run locally by llama.cpp. Everything that makes it behave like an editor comes from the system around it, described below. Where the code and prompts say "EditLM", that is the name reserved for the custom model in chapter 8.

Five techniques that make a small general model edit well

1. Measurements, not pixels

The model reads a short text brief of numbers the engine measured (exposure, motion, speech, beats). It never has to "look" at an image.

2. Grammar-constrained output

Generation is limited by a GBNF grammar built from the tool schemas, so the output always parses. It can only name looks and values that exist.

3. Hints as hard limits

Your words and the style/output options narrow the grammar itself: a chosen style fixes the pace, "TikTok" fixes 9:16, a vague request only allows safe looks.

4. Playbook and examples

The prompt carries a short editing playbook (shot variety, pacing per genre, few transitions) and worked examples of request to plan.

5. Guard rules after the model

Code re-checks the answer: values are clamped to what the media can take, and some decisions (keep captions if asked, no crossfades in a fast edit) cannot be overridden.

6. Code does the precise work

Exact cut points, beat alignment, crop framing and colour maths are deterministic code, which is always correct and repeatable.

What the grammar looks like

A shortened version of the grammar the video planner sends with each request. The model physically cannot write a line outside it.

root      ::= rationale nl aspect nl pace nl trans (nl look)? (nl fin){0,2} (nl caps)? (nl music)?
rationale ::= "# " [^\n]{3,120}
aspect    ::= "aspect " ("16:9" | "9:16" | "1:1" | "4:5")
pace      ::= "pace " ("fast" | "medium" | "slow")
trans     ::= "transition " ("none" | "crossfade" | "fade_black" | ...)
look      ::= "look " ("teal_orange_cinematic" | "golden_hour" | ...) " s=" ("0." [4-9] | "1" ("." [0-2])?)
fin       ::= ("grain 0." [0-3] [0-9] | "vignette 0." [1-4] | "bloom 0." [1-3])

Three versions, not one

The same request is sent three times with increasing "temperature" (0.2, 0.8, 1.1), from safe to adventurous, each with a fixed seed so results are repeatable. You see all three and pick.

Fallbacks

SituationWhat happens
Model not installedRule-based planners for photo and video produce programs from keywords and measurements. The app labels this "Rules only".
Model output weak (e.g. copies an example)The rationale is rewritten from the actual plan, and guard rules still apply.
Speech model missingCaptions and talk-based highlights are unavailable; visual and audio signals still drive edits.

06

Reels and captions

Finding the best moments

For a long talking video, the transcript is split into sentences and every possible window of the target length (for example 30 s) is scored. The score combines:

  1. Words. Hooks, questions, numbers, strong statements, complete sentences (text rules), plus a 1 to 5 rating of each sentence by the local model ("would this make people stop scrolling?"), itself grammar-limited to one digit per line.
  2. Sound. Loudness and energy peaks such as laughter or emphasis.
  3. Picture. Motion and visual change per second.

The best windows that do not overlap become the reels. Then pauses and filler words ("um", "you know") are cut using word timings, the speaker is tracked so a wide 16:9 shot becomes a well-framed 9:16 one, and captions, a progress bar and an optional end card are added.

Choosing the subject

Every photo and video has a subject: found automatically, or picked with one click.

  1. Automatic. A map of what usually makes a subject (in focus, different in colour from the edges of the frame, near a face, near the centre) seeds OpenCV's GrabCut, which then follows the real colour edges to cut the subject out.
  2. Picked by hand. In a photo, "Pick on photo" and a click; in a video, "Pick in viewer" shows the clip's original frame and you click the person or thing. The click becomes the seed for the same cut-out.
  3. Photos: the subject edit lights the subject or blurs, darkens or desaturates everything behind it (portrait mode, colour splash). Auto edit understands "blur the background", "make the product pop" and "colour splash".
  4. Videos: from the click, feature points on the subject are followed frame by frame with optical flow, forwards and backwards through the whole clip. "Follow subject" then moves the picture so the subject stays centred, which is what makes 16:9 footage work as a 9:16 reel. Reels use the picked subject automatically.

None of this needs a download. A dedicated segmentation model (for example BiRefNet or SAM2) can later replace GrabCut for hair-accurate edges.

Captions that stay out of the way

Captions are grouped from word timings (short chunks for bold reel captions), and the word being spoken is highlighted. Before export, the engine looks at a few frames under each caption, finds faces and any text already burned into the video (like a name title), and moves the caption to the spot that covers the least of them. Captions you placed by hand never move.

How quality is checked. 153 automated tests cover the engine (rendering maths, DSL round-trips, licensing, jobs, placement). Every larger feature was also run end to end on real footage, with frames inspected, before being called done.

08

The custom model, next

PLANNEDEditLM is the custom model that will replace the off-the-shelf one: a model of 2 billion parameters or fewer, trained only to drive this editor. Nothing in this chapter has been trained yet; it is the plan from the project roadmap.

What it will learn from

  1. An editing playbook written by us (about 300 rules with good and bad examples), used for knowledge, for the rationale line, and as an automatic linter.
  2. Expert recordings. Professional editors edit freely licensed media inside Framewise; the editor records their exact actions as edit programs. This is the most valuable data.
  3. Synthetic data. "Inverse edits": take a clean photo, apply a random look, have a teacher write the request that would produce it. For video, a large open teacher model plans edits that are executed in the engine; failures are dropped.
  4. Opt-in feedback. Which versions beta users keep or undo (only with consent).

How it will be trained

It will also get a small vision adapter so it can "see" a compact summary of each shot, not just the numbers. The shipped app will still run fully offline; large models are only used during training, never on users' machines.

09

Glossary

Edit DSL
The small text language every edit is written in (photo and video). Humans, the model and automations all use it.
Command bus
The single path through which the project changes; it records undo history.
Intent
The model's short video plan: shape, pace, transitions, look, captions, music.
Director
Plain code that turns an intent into an exact cut list.
Grammar (GBNF)
A rule set that limits what the model may write, so output always parses.
Brief
A short text summary of measurements given to the model instead of pixels.
llama.cpp / whisper.cpp
Open-source local runtimes for the language model and speech recognition.
Recipe
An automation job type such as reel, captions, photo_edit or render_program.
EditLM
The planned custom-trained editing model (not trained yet).
